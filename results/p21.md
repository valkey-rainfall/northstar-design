## PRE-C defaults that differ from S1 (kept as shipped)

- keyspace-shard-bits: default -1 = auto, resolved to 8 bits (256 shards) on every standalone server
  (resolveKeyspaceShardBits, src/server.c). S1 default is 0.
- One jemalloc arena per IO thread (zmalloc_bind_thread_arena from the IO thread start; no config).
- io-threads-epoll-thread: new, default no.
- io-threads-parallel-writes-min: default 32 (hidden). C9, D9 and AOF9 force 1 and keyspace-shard-bits 8 on
  both builds, as in the p17reg cells, so those cells compare the same lane settings.

## NO-TOUCH point: not run

On PRE-C the IO-thread LRU/LFU touch (src/fastget.c fastGetTouchBegin / fastGetTouch) is off only for a
client with CLIENT NO-TOUCH or while a child process runs. No server config turns it off, and
cachecannon has no per-connection setup command to send CLIENT NO-TOUCH. Running a child (BGSAVE) would
change much more than the touch. So the point needs a code change and is skipped, as instructed.
Note: under the default LRU policy the touch writes a key at most once per LRU clock tick; on other
reads it is one load and one compare (src/fastget.c:386).

## Finding: C refuses to start with io-threads-epoll-thread yes below io-threads 3

In the Figure 1 sweep, C ceaa1101d with `--io-threads 1` or `--io-threads 2` and
`--server-args "--io-threads-epoll-thread yes"` did not start (tasks 2026.11.07_04.19.30.413057 and
2026.11.07_04.19.36.010458, the runner "ProcessError: Process exited with non-zero exit status 1").
The config check `stagedEpollThreadConfigValid` (src/staged_loop.c:75-86, called from config.c at load
time and when io-threads or the setting changes) rejects the combination with this error text
(src/staged_loop.c:82):

    io-threads-epoll-thread needs io-threads 3 or more (the main thread, one I/O thread and the epoll thread)

The check is `on && io_threads < STAGED_EPOLL_THREAD_MIN_IO_THREADS + io_threads_epoll_threads - 1`, with
STAGED_EPOLL_THREAD_MIN_IO_THREADS 3 (src/staged_loop.c:70); with io-threads-epoll-threads N > 1 the limit is
io-threads N+2 and the message at src/staged_loop.c:78-79 is used instead. So the setting is not silently
ignored at low io-threads: a config that sets it is a startup error there. The doc's recommended setting
(io-threads-epoll-thread yes) must say "io-threads 3 or more".

Sweep handling (11-07): the 2 matching R2 tasks were cancelled; C at io1 and io2 runs with the default
config instead (label C, 4 tasks: 2026.11.07_04.52.35.992550, 04.52.38.058440, 04.52.40.148142,
